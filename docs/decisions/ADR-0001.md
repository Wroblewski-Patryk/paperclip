# ADR-0001: Map the autonomous softwarehouse model to existing Paperclip primitives

Status: Accepted

Date: 2026-07-02

## Context

The local LuckySparrow Software House needs an autonomous-company operating model with explicit
agent operating records, tasks, runs, trajectory logs, evidence, policy gates, supervisor reviews,
deployment checks, monitoring, retrospectives, and process improvement.

Paperclip already has durable V1 primitives for much of that model:

- `agents` represents the agent roster, role, reporting line, capabilities, runtime configuration,
  permissions, budget, and metadata.
- `issues` represents task work, parentage, single assignment, checkout/execution locks, status,
  work mode, priority, source trust, and workspace linkage.
- `heartbeat_runs` represents an agent execution attempt.
- `heartbeat_run_events` and `activity_log` represent trajectory and mutation logs.
- `issue_work_products`, issue documents, comments, attachments, and approvals represent evidence
  and review artifacts.

Creating parallel tables named `AgentTask`, `AgentRun`, or `AgentEvidence` would fragment the V1
contract unless a query or enforcement need proves that the existing primitives cannot support it.

## Decision

Paperclip V1 maps the autonomous softwarehouse vocabulary onto existing control-plane primitives:

- AgentOperatingRecord: `agents` plus `agents.runtime_config`, `agents.permissions`, budgets,
  metadata, recent `heartbeat_runs`, recent `activity_log`, and issue/work-product metrics.
- AgentTask: `issues`, including hierarchy, assignment, checkout, execution lock, labels,
  documents, comments, approvals, and work products.
- AgentRun: `heartbeat_runs`, with run intent stored in invocation source, result payload,
  issue linkage, and final report fields.
- AgentRunEvent / Trajectory Log: `heartbeat_run_events` plus `activity_log` for durable events.
- AgentEvidence: `issue_work_products`, issue documents, attachments, approvals, deployment
  records, monitoring records, and review comments linked to the issue and run.
- AgentControlPolicy: company/project/agent configuration, runtime permissions, approval gates,
  budget policies, path/workspace policy, and the policy-gate documents in this docs set.
- AgentSupervisorReview: issue approvals, issue thread interactions, supervisor-owned review
  issues, and activity log entries until a dedicated normalized read model is justified.

## Consequences

Agents must use the aliases above when auditing, planning, implementing, testing, reviewing, and
deploying work. Documentation and dashboards should show the softwarehouse vocabulary, but services
should continue to enforce company scoping, assignment locks, budget stops, approvals, and activity
logging through the canonical tables.

The remaining gaps are enforcement gaps rather than naming gaps:

- hard evidence gates before `done`;
- structured supervisor-review summaries;
- a single mission-control surface for SDLC stage, gate state, and evidence coverage;
- normalized operating-record projections if query complexity becomes too high;
- automated PDCA issue creation for repeated failures and stalled deployment/monitoring cycles.
