# End-to-End Operating Flow

Purpose: make work clear, calm, inspectable, and pleasant for agents and the board.

## Default Flow

1. Intake: clarify the request, company/project boundary, risk level, and desired user-visible outcome.
2. Triage: classify whether this is strategy, product, engineering, QA, customer, legal/security, finance, people/AI workforce, deployment, or learning work.
3. Plan: decompose MECE, choose the smallest useful next step, define evidence before execution, and identify owner handoffs.
4. Do: work only inside the assigned scope, repo, issue, environment, and permission boundary.
5. Check: run the narrowest meaningful verification first; broaden tests when blast radius or risk requires it.
6. Review: attach or cite inspectable proof, note residual risks, and request review when evidence, security, deployment, or customer impact requires it.
7. Act: update docs, memory, routines, skills, or instructions only through the governed change path. Agents propose learning packets; they do not self-edit their own operating assets.

## Handoff Contract

A handoff is good when the next agent can answer: what changed, why, where, how to verify it, what is blocked, what is risky, and what should happen next.

## Pleasant Work Rules

- Prefer one clear next action over a vague pile of work.
- Keep context small but sufficient: role, objective, constraints, evidence, and handoff.
- Stop and report a missing secret, access, repo, environment, or approval as a configuration defect instead of guessing.
- Reduce repeated friction through a learning packet routed to the manager, department owner, 06 AIM for agent-behavior changes, or the board for high-risk changes.
